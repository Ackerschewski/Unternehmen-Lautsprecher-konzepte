# Warum dieses Paket nötig ist

3D darf nicht nur hübsch aussehen. Geometrie, Kollision, Zeichnung, BOM und später STEP müssen auf demselben parametrischen Kern beruhen.

Der aktuelle Stand ist bereits funktionsreich. Der nächste Qualitätssprung entsteht nicht durch weitere isolierte Buttons, sondern durch belastbare Modelle, gemeinsame Datenstrukturen, transparente Unsicherheit, reproduzierbare Tests und eine klarere Verbindung von Planung → Simulation → Konstruktion → Fertigung.

# Workstreams

## A. Canonical Geometry Model

- Panel, Cutout, Hole, Pocket, DriverEnvelope, Port, Brace, Divider, TreatmentRegion.
- Lokale Koordinatensysteme und Transformationen.
- Keine UI-spezifischen Geometrieobjekte.

### Abnahme A
- [ ] Eine Szene speist 3D, Zeichnung und Kollision.
- [ ] Serialisierung vorhanden.
- [ ] Einheiten SI.

## B. Collision Engine

- Treiberkorb vs. Wand/Strebe/Port.
- Magnet vs. Rückwand.
- Port vs. Rückwand/Strebe/Treiber.
- PR vs. Innenkomponenten.
- Bohrung/Ausschnitt vs. Kante.
- Dämmung vs. Port-Keepout.

### Abnahme B
- [ ] Kollisionen mit Tiefe/Delta gemeldet.
- [ ] Export kann harte Fehler blockieren.
- [ ] Tests für bekannte Konflikte.

## C. Joinery Geometry

- Stumpf, Gehrung, Falz, Nut/Dado, doppelte Front, eingelassene Rückwand.
- Verbindungstyp verändert Geometrie und Zuschnitt korrekt.
- Innenvolumen bleibt korrekt.

### Abnahme C
- [ ] Mindestens vier Verbindungstypen.
- [ ] Volumen-/Cutlist-Regressionen.

## D. 3D Renderer 2.0

- Orbit, Zoom, ISO/Front/Side/Top, Transparenz, Section Plane, Exploded View Basis.
- Objektselektion → Inspector.
- Warnungen markieren betroffene Objekte.

### Abnahme D
- [ ] Interaktiv stabil.
- [ ] Selection funktioniert.
- [ ] Kein Fake-CAD.

## E. Mounting Path & Serviceability

- Optional vereinfachter Einbauweg für Treiber/Weiche.
- Prüfen, ob Bauteil durch Öffnung montierbar ist.
- Werkzeug-/Schraubzugang als spätere Heuristik vorbereiten.

### Abnahme E
- [ ] Mindestens Treiber-Montageweg prüfbar.
- [ ] Fehler verständlich.

## F. Geometry Performance

- Scene caching.
- Keine Akustik-Neuberechnung bei Kamerabewegung.
- Große 3-Wege-Projekte flüssig.

### Abnahme F
- [ ] Kamera <100 ms Reaktion.

# Architekturregeln

- Core/Domain darf nicht von PySide6 abhängen.
- Solver, Optimierer, Library und Geometrie bleiben separat testbar.
- Einheiten intern SI.
- UI formatiert Werte und Einheiten.
- Projektdatei erhält bei Schemaänderungen Migrationen.
- Ein einziges kanonisches Projektmodell.
- Keine doppelte Geometrie für UI und Fertigung.
- Datenprovenienz bleibt erhalten.
- Fehlerzustände werden als strukturierte Objekte modelliert, nicht nur als freie Strings.
- Ergebnisse müssen reproduzierbar sein.
- Zufallsbasierte Optimierung nur mit explizitem Seed und dokumentierter Deterministik.

# Daten- und Vertrauensregeln

- Reale Daten brauchen Quelle, Abruf-/Messdatum und Status.
- Abgeleitete Werte müssen als abgeleitet gekennzeichnet werden.
- Schätzwerte dürfen niemals still wie Herstellerdaten aussehen.
- Datenvollständigkeit beeinflusst Assistent und Score.
- Aussagen wie „beste“, „günstigste“, „lauteste“ oder „linearste“ sind nur zulässig, wenn die Vergleichsgrundlage vollständig genug ist.
- Für experimentelle Modelle wird im Projekt und Export ein Vertrauensstatus mitgeführt.
- Der Nutzer muss erkennen können, welche Teile gemessen, berechnet, geschätzt oder unbekannt sind.

# Detailed Execution Extension

## User Journeys

### Journey 1 – Mechanical feasibility before export
A driver physically fits the front cutout but its magnet collides with a window brace. The design is marked mechanically invalid, the collision is highlighted in 3D and manufacturing export is blocked.

### Journey 2 – Joinery change
Switch rear panel from butt joint to rebate. Panel dimensions, net volume, cut list, drawing and 3D all update from the same geometry.

### Journey 3 – Transparent inspection
User hides front/side panels, sees port, braces, crossover and acoustic treatment, clicks an object and receives exact dimensions/source confidence in the inspector.

## Geometry Precision Policy

Define model tolerances:
- geometric epsilon
- collision contact vs overlap
- minimum manufacturing clearance
- display tessellation tolerance

Never use viewport mesh approximation as the authoritative manufacturing geometry.

## Scene / Solid Separation

The renderer may consume triangulated/display geometry, but authoritative geometry remains the canonical panel/solid feature model. STEP/DXF and collision must not depend on screen tessellation.

## Collision Severity

Classify:
- hard collision
- insufficient clearance
- near-edge manufacturing warning
- unknown due to missing component envelope

Unknown geometry must not become "clearance passed".

## Selection Contract

Every selectable 3D object maps to a stable project entity ID. Selection must survive camera changes and should survive recomputation when the same entity still exists.

## Performance Benchmarks

Measure:
- scene build;
- collision pass;
- viewport update;
- section/explode;
- complex 3-way enclosure.

## Additional Evidence

- deliberate brace/driver collision;
- port/back-wall clearance;
- rebated panel section;
- transparent internal view;
- object selection + inspector.

## Additional Acceptance

- [ ] Collision engine works without PySide.
- [ ] Display mesh is not the manufacturing source of truth.
- [ ] Unknown component geometry cannot produce false PASS.
- [ ] Joinery changes propagate to volume/cutlist.
- [ ] Stable entity IDs connect 3D, BOM, warnings and drawings.
