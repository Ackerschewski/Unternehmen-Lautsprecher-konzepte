## Type
FEATURE / ARCHITECTURE / VALIDATION / UX / TEST / DOCUMENTATION

## Goal

Baue eine systematische QA-Infrastruktur, die numerische Regressionen, Projektmigrationen, UI-Flows, Exporte, Visual Evidence und Build-Smokes reproduzierbar abdeckt.

# 1. Autonomous Execution Contract

Claude soll nach Freigabe dieses Tasks mehrere Stunden bzw. mehrere zusammenhängende Sessions selbstständig daran arbeiten.

Verbindliche Regeln:

1. Aktuellen Integrationsbranch, Blackboard, PROJECT_STATUS, ARCHITECTURE und alle Dependencies lesen.
2. Baseline ausführen: pytest, Ruff, mypy Non-UI, relevanter Smoke-Test.
3. Vor Änderungen existierende APIs und Modelle wiederverwenden.
4. Keine zweite parallele Implementierung derselben Domäne.
5. Core vor UI.
6. Keine erfundenen Hersteller-, Preis-, Mess-, Geometrie- oder Materialdaten.
7. Unbekannt ist ein eigener Zustand und niemals implizit 0.
8. Jeder neue Solver/Algorithmus dokumentiert Modellannahmen, Gültigkeitsbereich und Unsicherheit.
9. Neue Projektfelder brauchen Migration.
10. Jede UI-Aussage muss aus strukturierten Daten stammen; keine heuristischen Marketinglabels ohne belastbare Grundlage.
11. Nach jedem größeren Workstream Tests ausführen.
12. Eigenständig Fehler korrigieren.
13. Nicht nach jedem Commit oder Teilbereich auf ein neues „mach weiter“ warten.
14. Falls ein externer Blocker entsteht: dokumentieren, nächsten unabhängigen Workstream fortsetzen.
15. NOT_RUN bleibt NOT_RUN.
16. Keine Funktion als abgeschlossen markieren, wenn nur UI ohne Kernlogik existiert.
17. Keine Core-Funktion als abgeschlossen markieren, wenn die reale Nutzerstrecke sie nicht erreichen kann.
18. Am Ende vollständigen Buildreport, Evidence und Handoff erzeugen.

# 2. Warum jetzt

Die Testzahl ist bereits hoch, aber mit wachsender Architektur braucht das Projekt klar definierte Ebenen, Fixture-Korpora, Golden Data, Performance Budgets und reale Release-Gates.

Der aktuelle Lautsprecher-Konstruktor hat bereits viele Funktionen. Das Risiko besteht deshalb zunehmend nicht in zu wenig Funktionsumfang, sondern in inkonsistenter Tiefe: einzelne Bereiche sind sehr weit, andere bestehen aus Näherungen oder fehlen im realen Workflow. Dieser Task soll die betreffende Domäne von „vorhanden“ zu „belastbar verwendbar“ bringen.

# 5. Domain / Data Contract

Neue oder geänderte Modelle müssen:

- eindeutig versionierbar sein;
- SI intern verwenden;
- fehlende Werte als Optional/Unknown behandeln;
- Herkunft/Trust getrennt vom numerischen Wert führen;
- projektpersistierbar sein;
- migrationsfähig sein;
- durch Library-Referenzen nicht unkontrolliert veränderbar werden;
- bei Projekt-Snapshot die für Reproduzierbarkeit nötigen Daten sichern;
- zwischen berechnet, gemessen, Herstellerwert, Nutzerwert und Schätzung unterscheiden.

Für Resultate:

- numerischer Wert;
- Einheit;
- Confidence/Trust, falls relevant;
- Quelle/Modell;
- Warnungen;
- Gültigkeitsbereich;
- ggf. Frequenzachse;
- ggf. limitierender Mechanismus.

Keine freie String-API als primärer Datenträger.

---

# 6. Service Architecture

Die neue Funktionalität soll über klar benannte Services/Use Cases erreichbar sein.

Anforderungen:

- UI ruft Services auf, keine Solver direkt aus Widgets;
- CLI/Test kann denselben Service verwenden;
- AutomaticDesignService kann relevante Resultate konsumieren;
- Exporter erhalten aufgelöste Resultate;
- Caching nur auf immutable/reproduzierbaren Inputs;
- lange Operationen abbrechbar;
- Progress strukturiert melden;
- Threading/Worker nicht in Solverlogik einbauen.

---

# 7. UI / UX Principles

Simple Mode:

- nur Entscheidungen, die der Nutzer verstehen muss;
- Defaults erklären;
- Unsicherheit und fehlende Daten sichtbar, aber nicht alarmistisch;
- keine Rohparameterwand.

Expert Mode:

- vollständige Parameter;
- Modellannahmen;
- Quellen;
- Diagnose;
- manuelle Overrides.

Visualisierung:

- große Arbeitsfläche;
- synchronisierte Auswahl zwischen Plot/3D/Inspector;
- Warnung anklicken → relevante Stelle;
- Einheiten konsistent;
- Nullwerte nicht als „0“ ausgeben, wenn unbekannt;
- Light/Dark;
- 1280×720 bleibt vollständig nutzbar;
- 1920×1080 nutzt zusätzliche Fläche für Daten/Visualisierung statt breitere Formulare.

---

# 8. Automatic Design Integration

Die Automatik muss die neuen Daten/Funktionen verwenden können.

Regeln:

- nur ausreichend vertrauenswürdige Resultate dürfen harte Auswahlentscheidungen steuern;
- unvollständige Daten reduzieren Confidence statt falsche Präzision zu erzeugen;
- experimentelle Modelle dürfen Varianten liefern, aber müssen markiert und ggf. niedriger priorisiert werden;
- Reject Reasons strukturiert;
- „nicht machbar“ muss konkrete Constraint-Informationen liefern;
- Score-Breakdown darf nur Kriterien enthalten, die tatsächlich berechnet wurden;
- neue Kriterien brauchen normalisierte, dokumentierte Skalen;
- Score allein ist kein Ersatz für Pareto-/Constraint-Logik.

---

# 9. Export / Reporting

Relevante neue Informationen müssen dort erscheinen, wo sie fachlich gebraucht werden:

- Projektzusammenfassung;
- PDF;
- CSV/JSON;
- Zeichnung/3D;
- BOM/Fertigung, falls materiell;
- Simulationsexport, falls numerisch.

Exports müssen:

- Einheiten nennen;
- Modell-/Messstatus nennen;
- fehlende Daten nicht verschweigen;
- Projekt-Revision enthalten;
- reproduzierbar sein.

---

# 10. Performance Targets

- Fast suite target <90 s where realistic.
- Full suite parallelizable.
- Performance regressions flagged by thresholds not noisy microseconds.

Zusätzlich:

- UI bleibt während längerer Operationen bedienbar;
- Cancel wird respektiert;
- Resize löst keine Kern-Neuberechnung aus;
- Caches invalidieren deterministisch;
- 1000+ Library-Komponenten dürfen Standardfilter nicht spürbar blockieren;
- numerische Frequenzvektoren möglichst vektorisiert verarbeiten.

Performance-Messwerte im Buildreport dokumentieren.

---

# 11. Migration / Backward Compatibility

- Bestehende Projekte müssen weiter ladbar sein.
- Neue Felder mit sicheren Defaults/Unknown.
- Migrationen idempotent testen.
- Vor destruktiver Migration Backup/Snapshot.
- Alte Resultate, die nach neuer Logik nicht mehr vertrauenswürdig sind, neu berechnen statt still weiterverwenden.
- UI muss alte Projekte mit klarer Migrationsmeldung öffnen können.
- Demo-Projekte aktualisieren.
