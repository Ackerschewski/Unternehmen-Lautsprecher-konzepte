# 2. Warum jetzt

Viele große Workstreams können einzeln grün sein und zusammen trotzdem widersprüchlich werden. V4 braucht eine eigene Integrationsphase mit realen End-to-End-Szenarien, Build, Migration, Evidence und Owner-Abnahme.

Der aktuelle Lautsprecher-Konstruktor hat bereits viele Funktionen. Das Risiko besteht deshalb zunehmend nicht in zu wenig Funktionsumfang, sondern in inkonsistenter Tiefe: einzelne Bereiche sind sehr weit, andere bestehen aus Näherungen oder fehlen im realen Workflow. Dieser Task soll die betreffende Domäne von „vorhanden“ zu „belastbar verwendbar“ bringen.

# 5. Domain / Data Contract

Neue oder geänderte Modelle müssen:

- eindeutig versionierbar sein;
- SI intern verwenden;
- fehlende Werte als Optional/Unknown behandeln;
- Herkunft/Trust getrennt vom numerischen Wert führen;
- projektpersistierbar sein;
- migrationsfähig sein;
- durch Library-Referenzen nicht unkontrolliert veränderbar werden;
- bei Projekt-Snapshot die für Reproduzierbarkeit nötigen Daten sichern;
- zwischen berechnet, gemessen, Herstellerwert, Nutzerwert und Schätzung unterscheiden.

Für Resultate:

- numerischer Wert;
- Einheit;
- Confidence/Trust, falls relevant;
- Quelle/Modell;
- Warnungen;
- Gültigkeitsbereich;
- ggf. Frequenzachse;
- ggf. limitierender Mechanismus.

Keine freie String-API als primärer Datenträger.

---

# 6. Service Architecture

Die neue Funktionalität soll über klar benannte Services/Use Cases erreichbar sein.

Anforderungen:

- UI ruft Services auf, keine Solver direkt aus Widgets;
- CLI/Test kann denselben Service verwenden;
- AutomaticDesignService kann relevante Resultate konsumieren;
- Exporter erhalten aufgelöste Resultate;
- Caching nur auf immutable/reproduzierbaren Inputs;
- lange Operationen abbrechbar;
- Progress strukturiert melden;
- Threading/Worker nicht in Solverlogik einbauen.

---

# 7. UI / UX Principles

Simple Mode:

- nur Entscheidungen, die der Nutzer verstehen muss;
- Defaults erklären;
- Unsicherheit und fehlende Daten sichtbar, aber nicht alarmistisch;
- keine Rohparameterwand.

Expert Mode:

- vollständige Parameter;
- Modellannahmen;
- Quellen;
- Diagnose;
- manuelle Overrides.

Visualisierung:

- große Arbeitsfläche;
- synchronisierte Auswahl zwischen Plot/3D/Inspector;
- Warnung anklicken → relevante Stelle;
- Einheiten konsistent;
- Nullwerte nicht als „0“ ausgeben, wenn unbekannt;
- Light/Dark;
- 1280×720 bleibt vollständig nutzbar;
- 1920×1080 nutzt zusätzliche Fläche für Daten/Visualisierung statt breitere Formulare.

---

# 8. Automatic Design Integration

Die Automatik muss die neuen Daten/Funktionen verwenden können.

Regeln:

- nur ausreichend vertrauenswürdige Resultate dürfen harte Auswahlentscheidungen steuern;
- unvollständige Daten reduzieren Confidence statt falsche Präzision zu erzeugen;
- experimentelle Modelle dürfen Varianten liefern, aber müssen markiert und ggf. niedriger priorisiert werden;
- Reject Reasons strukturiert;
- „nicht machbar“ muss konkrete Constraint-Informationen liefern;
- Score-Breakdown darf nur Kriterien enthalten, die tatsächlich berechnet wurden;
- neue Kriterien brauchen normalisierte, dokumentierte Skalen;
- Score allein ist kein Ersatz für Pareto-/Constraint-Logik.

# Extended Execution Annex – mandatory scope depth

This annex is mandatory for TASK-0050 (V4 Integration, Release Candidate & Product Acceptance). It raises the workstream to full product-slice depth and prevents completion based only on a narrow visible feature.

## 1. Deliverables

All applicable deliverables must exist together:

1. versioned domain/data model;
2. migration and backward compatibility;
3. core/service implementation;
4. structured diagnostics/errors;
5. Simple Mode policy;
6. Expert Mode inspection path;
7. Automatic Design integration review;
8. project persistence;
9. export/report implications;
10. deterministic tests;
11. regression fixtures;
12. performance classification;
13. real UI/evidence where applicable;
14. technical and user documentation;
15. buildreport and handoff.

A non-applicable deliverable needs a written reason.

## 2. Integration Boundary Audit

Review every relevant boundary:

- Library ↔ project snapshot
- project ↔ service
- service ↔ AutomaticDesign
- result ↔ diagnostics
- result ↔ UI/3D/plot/inspector
- project/result ↔ BOM/drawing/export
- project ↔ save/load/migration/recovery
- feature ↔ demo projects
- feature ↔ V4 workspace
- feature ↔ QA/release gate

No two layers may independently calculate the same business value with different logic.

## 3. Data-state semantics

Every technical field/result belongs to one state:

- VERIFIED
- LOWER_TRUST
- DERIVED
- USER_OVERRIDE
- UNKNOWN
- NOT_APPLICABLE
- UNSUPPORTED

Unknown is never numeric zero. Unsupported is never failure if the product intentionally does not implement the model.

## 4. Structured diagnostics

Important errors/warnings carry:
- code;
- severity;
- entity;
- German message;
- actual value;
- required/limit value;
- unit;
- frequency/position if relevant;
- source/model;
- verified remediation when available.

Normal users should not see raw exception fragments.

## 5. Product-truth language

Review labels and prose for unsupported strength. Terms such as best, optimal, cheapest, exact, safe, validated, linear, maximum or manufacturing-ready require a defined scope and evidence.

Prefer explicit qualifiers:
- calculated;
- estimated;
- preliminary;
- based on known prices;
- based on available measurements;
- reference-verified;
- prototype-validated.

## 6. UI depth

### Simple Mode
- no raw technical wall;
- understandable decisions;
- clear confidence/data gaps;
- direct next action.

### Expert Mode
- parameters;
- sources;
- diagnostics;
- raw result detail;
- controlled override.

### Responsive
At 1280×720:
- no clipping;
- no horizontal scroll for primary workflow;
- visualization remains meaningful.

At 1920×1080:
- visualization/data context grows;
- forms remain sensibly bounded.

### Accessibility
- focus visible;
- keyboard path;
- non-color-only warnings;
- reasonable DPI behavior.

## 7. Performance classification

Every operation introduced/changed must be labelled:
- instant <100 ms;
- interactive <300 ms;
- short background <2 s;
- long background >2 s.

Long operations need progress/cancel where feasible. Stale background results must never overwrite newer project state.

Caches require:
- stable input hash;
- explicit invalidation;
- regression test;
- diagnostic stats where useful.

## 8. Migration procedure

For every schema change:
1. old fixture;
2. migration;
3. validate;
4. save;
5. reload;
6. semantic comparison.

If algorithm changes invalidate cached results, mark stale and recompute. Never silently keep incompatible old output.

## 9. Required fixture set

At minimum:
- reference/simple case;
- realistic project;
- incomplete-data project;
- edge/error case;
- migrated old project.

Assertions should verify real semantics/ranges.

## 10. Manual self-review

Before handoff verify:

- same value across UI/export;
- no unknown-as-zero;
- no stale results after errors;
- variant switch updates dependent views;
- save/reload exact enough for reproducibility;
- units correct;
- warning navigation useful;
- missing data visible;
- model limitations discoverable;
- 1280 workflow still usable.

Fix or document each failure.
