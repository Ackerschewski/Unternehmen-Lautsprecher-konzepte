## Type
FEATURE / ARCHITECTURE / VALIDATION / UX / TEST

# Warum dieses Paket nötig ist

Alle akustischen Kernsolver brauchen nachvollziehbare Vertrauensstufen, Referenzfälle und systematische Vergleichbarkeit, bevor weitere Automatik sie als gleichwertig behandeln darf.

Der aktuelle Stand ist bereits funktionsreich. Der nächste Qualitätssprung entsteht nicht durch weitere isolierte Buttons, sondern durch belastbare Modelle, gemeinsame Datenstrukturen, transparente Unsicherheit, reproduzierbare Tests und eine klarere Verbindung von Planung → Simulation → Konstruktion → Fertigung.

# Workstreams

## A. Solver Registry & Trust Levels

- Jeder Solver erhält ID, Familie, Modellversion, Trust-Level und bekannte Grenzen.
- Trust-Level mindestens FORMULA_VERIFIED, REFERENCE_VERIFIED, PROTOTYPE_VALIDATED, EXPERIMENTAL.
- Assistent darf EXPERIMENTAL nicht gleichrangig wie validierte Modelle behandeln.
- Vertrauensstatus in Expertenmodus und Export sichtbar machen.

### Abnahme A
- [ ] Alle Solver registriert.
- [ ] Trust-Level beeinflusst Auswahl/Anzeige.
- [ ] Keine stillen EXPERIMENTAL-Solver im Favoritenranking.

## B. Literatur- und Referenzfälle

- Closed, Bassreflex, PR, Bandpass 4/6, Isobarik, Open Baffle, TL/MLTL und Hornfamilien mit numerischen Referenzfällen absichern.
- Referenzwerte mit Quelle und Toleranz dokumentieren.
- Bei Solverfamilien ohne belastbare Referenz zuerst Modellgrenze dokumentieren statt Fantasie-Targets.

### Abnahme B
- [ ] Mindestens ein numerischer Referenzfall je unterstützter Solverfamilie.
- [ ] Quellen in Maintenance dokumentiert.
- [ ] Toleranzen technisch begründet.

## C. Cross-Solver Consistency

- Gemeinsame Größen wie Vb, Fb, F3, Portfläche, Gruppenlaufzeit, Impedanz und SPL auf konsistente Einheiten/Definitionen prüfen.
- Identische Eingaben dürfen nicht wegen unterschiedlicher Konventionen widersprüchliche Metadaten erzeugen.
- Sanity-Checks für Grenzwerte und extreme Eingaben.

### Abnahme C
- [ ] Einheiten konsistent.
- [ ] Sanity-Suite vorhanden.
- [ ] Extremfälle liefern strukturierte Fehler statt NaN/Crash.

## D. Reference Harness

- CLI/Service zum Durchlaufen aller Referenzfälle.
- Maschinenlesbare Ergebnisdatei für Regression.
- Diff-Ansicht zwischen aktuellem und gespeicherten Referenzstand.

### Abnahme D
- [ ] Ein Befehl prüft alle Referenzfälle.
- [ ] Regressionen werden quantitativ ausgegeben.
- [ ] Baseline versioniert.

## E. Validation UI

- Expertenansicht 'Modellvertrauen' mit Solverstatus, Referenzquelle und bekannten Grenzen.
- Keine Überfrachtung im Simple Mode; dort nur Warnung bei experimentellem Modell.

### Abnahme E
- [ ] Trust-Information auffindbar.
- [ ] Simple Mode bleibt ruhig.

## F. Documentation & Governance

- Validation Matrix erstellen.
- Regel definieren, wann ein Solver von EXPERIMENTAL auf REFERENCE_VERIFIED/PROTOTYPE_VALIDATED wechseln darf.

### Abnahme F
- [ ] Matrix vollständig.
- [ ] Promotion-Regeln dokumentiert.

# Architekturregeln

- Core/Domain darf nicht von PySide6 abhängen.
- Solver, Optimierer, Library und Geometrie bleiben separat testbar.
- Einheiten intern SI.
- UI formatiert Werte und Einheiten.
- Projektdatei erhält bei Schemaänderungen Migrationen.
- Ein einziges kanonisches Projektmodell.
- Keine doppelte Geometrie für UI und Fertigung.
- Datenprovenienz bleibt erhalten.
- Fehlerzustände werden als strukturierte Objekte modelliert, nicht nur als freie Strings.
- Ergebnisse müssen reproduzierbar sein.
- Zufallsbasierte Optimierung nur mit explizitem Seed und dokumentierter Deterministik.

---

# Daten- und Vertrauensregeln

- Reale Daten brauchen Quelle, Abruf-/Messdatum und Status.
- Abgeleitete Werte müssen als abgeleitet gekennzeichnet werden.
- Schätzwerte dürfen niemals still wie Herstellerdaten aussehen.
- Datenvollständigkeit beeinflusst Assistent und Score.
- Aussagen wie „beste“, „günstigste“, „lauteste“ oder „linearste“ sind nur zulässig, wenn die Vergleichsgrundlage vollständig genug ist.
- Für experimentelle Modelle wird im Projekt und Export ein Vertrauensstatus mitgeführt.
- Der Nutzer muss erkennen können, welche Teile gemessen, berechnet, geschätzt oder unbekannt sind.

# Detailed Execution Extension

## User Journeys

### Journey 1 – Closed/Bassreflex confidence check
A developer selects one known reference driver and runs sealed and vented reference cases. The UI shows equation source, solver version, trust level, expected tolerance and the numerical delta against the stored reference.

### Journey 2 – Experimental enclosure
A user selects a complex horn/TL family. The application may calculate it, but must show EXPERIMENTAL/REFERENCE_VERIFIED status and must not silently rank it equal to a prototype-validated closed box.

### Journey 3 – Regression after code change
A solver change runs the full reference harness and produces a machine-readable diff identifying which metrics changed beyond tolerance.

## Data Contract

Add or consolidate structured records such as:

- SolverDescriptor
- SolverTrustLevel
- ReferenceCase
- ReferenceExpectation
- ValidationRun
- ValidationDifference
- ModelLimitation

Each reference expectation stores metric, value, unit, tolerance type, tolerance value and source.

No free-form markdown alone may serve as the source of truth for automated validation.

## Performance

- Full reference harness should be fast enough for normal development use.
- Expensive advanced solvers may be marked slow and separated into a full suite.
- Reference data load must be deterministic.
- No UI repaint should trigger solver validation.

## Failure Policy

- NaN/Inf is always a failed case unless explicitly expected.
- Missing required solver output is failure, not zero.
- A changed formula source or convention requires a version bump and explicit baseline review.
- Updating golden reference values merely to make tests green is forbidden without documented technical justification.

## Evidence Matrix

Create:
- solver trust overview;
- one passing sealed reference case;
- one intentionally failed/diff example;
- one experimental solver warning;
- validation summary JSON/Markdown.

## Risk Register

- Reference circularity: never validate a solver only against values generated by itself.
- Convention mismatch: define volume, F3, Fb, impedance and SPL conventions centrally.
- Overconfidence: prototype validation is a distinct level and cannot be inferred from literature-only agreement.

## Migration

Existing projects without solver metadata load with the current registered solver descriptor. Saved results should not pretend historical solver identity if it was never persisted; show unknown/legacy where necessary.

- [ ] Every registered enclosure solver has a descriptor.
- [ ] Every SUPPORTED solver has at least one reference case.
- [ ] Experimental solvers are visibly distinct.
- [ ] Reference baselines cannot be silently regenerated.
